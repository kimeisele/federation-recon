## Disposition

### tier1a-001 — fixed

> A malformed or missing completion-token field is treated as zero, so the actual_known_totals budget can silently under-report and the cap never reflects real usage.

Commit `6d0be7b` adds `budget.actual_usage_complete`. Numeric known sums remain
telemetry; the boolean is false when any attempted provider call omits
`prompt_tokens` or `completion_tokens`. The schema, specification, missing-usage
test, and complete-usage test were updated together. The specification now also
states explicitly that request limits are the enforced guard and provider usage
is reported telemetry, not client-side enforcement of provider behavior.

### tier1a-002 — rejected

> The python embedder references $REVIEW_MODEL for the success artifact but the changed caller never passes it, producing output_model: null in live runs.

The claim is factually false. The parser invocation passes `REVIEW_MODEL` as its
seventh Python argument, and the live artifact recorded both
`requested_model: deepseek-v4-flash` and
`response_model: deepseek-v4-flash`. The existing test "model provenance records
the response model, not the requested model" also passed. The finding was marked
confirmed only because its command grepped for strings and exited zero; it did
not test the asserted data flow.

### tier1a-003 — rejected

> Cap reservation is computed from .request.json files, but if the request-file step is ever skipped or moved, remaining budget and requested_total can be zero even after model calls.

The request file is the payload passed directly to curl with
`--data @<request-file>`. In the current mechanism a provider dispatch cannot
occur through `_tier_call` without that file first being written. A hypothetical
future rewrite that removes this invariant is not a defect in this diff and
would have to update the cap-reservation tests.

### tier1a-004 — fixed in claim and fail-closed handling

> The PR claims per-run cap enforcement, but the enforcement is inferred from recorded requested_max_tokens, not from a provider-observed total; silent provider-side truncation or over-usage is not detected.

The specification now distinguishes request-side enforcement from provider
telemetry. Commit `6d0be7b` additionally fails a tier when the provider reports
`completion_tokens` equal to or greater than the requested maximum, even when
`finish_reason` is `stop`; exact-cap and over-cap tests prove Tier 1B is not run
and the verdict is `PARTIAL`. A client cannot force a non-conforming remote
provider to honor `max_tokens`; it can refuse to accept the response and record
the mismatch, which is what this mechanism now does.

### tier1a-005 — rejected

> write_verdict recomputes requested_total from .request.json files, overriding the builder's accumulator, so any mismatch between the two paths would be silently hidden.

The request artifacts are the authoritative record of reservations actually
prepared for dispatch. The shell function is called through command
substitution, so its local accumulator is not an independent durable source of
truth. Recomputing from the payloads avoids claiming state that did not leave the
subshell. The cap-reservation test verifies 6,000 + 4,000 = 10,000 in those
artifacts and in the verdict.

### tier1a-006 — rejected

> Budget accounting relies on glob(pattern) which silently returns an empty list on permission errors or directory read failures, so an unreadable run_dir would report zero instead of an error.

The verdict is written into the same `run_dir`. If that directory is unreadable
or unwritable, verdict assembly cannot produce a successful approval artifact.
The claimed plausible-success path was not demonstrated, and the finding had no
verification command.

### tier1a-007 — rejected with executed integration evidence

> No test exercises the real integration point between scripts/review.sh and scripts/gate.sh for the new budget schema or fail-fast behavior.

The review that produced this finding was the mechanism's integration run
against its own PR. It bound a detached worktree to the reviewed SHA, ran
`scripts/gate.sh --full` to PASS (650 tests), made two bounded provider calls,
validated their structured artifacts, executed finding commands, and assembled
a schema-valid aggregate verdict. Focused provider-stub tests cover the
fail-fast branches without paid calls.

### tier1b-001 — fixed where substantive

> [timeout] The new provisioning logic (the diff that introduces it) is configured but correctness is untested end-to-end: the only new 'retains usage' test uses a mock that never exercises the rewritten error-path writer, so a real truncation leaves usage out of the verdict.

The finding was inconclusive and its verification command timed out. The
substantive telemetry ambiguity is fixed by `actual_usage_complete`; truncation
already preserves returned usage, and the focused test asserts the exact
11/7/3 totals. Commit `6d0be7b` also adds exact-cap and over-cap fail-closed
tests. A curl failure cannot return provider usage; its artifact now has direct
status, error, provenance, requested-cap, and Tier 1B-not-run assertions.

### tier1b-002 — rejected; test strengthened

> The 'Tier 1B is not run after any Tier 1A error' gate is tested, but the error-artifact writer (rewritten to inline JSON) is only tested for the truncation path; the fallback to _write_tier_error when the artifact file is absent is never exercised, so its change could silently regress.

The existing mock curl-failure test executes `_write_tier_error`; the reviewer's
grep command did not execute or mutate that path. Commit `6d0be7b` strengthens
the test to assert the generated error artifact's status, message, provider,
requested model, absent response model, requested cap, Tier 1B reason, and
`PARTIAL` aggregate verdict.

### tier1b-003 — rejected as outside the control's threat boundary

> A self-interested author could claim low requested_total by deleting the .request.json files or by not writing them; the budget is additive and not enforced upstream, so the gate's own accounting is not tied to any limit.

A process with permission to delete live review payloads can also edit or
replace the runner itself; filesystem integrity against the host operator is not
the claimed control. Within the runner, request files are created before curl
uses them, the remaining budget is reserved before each dispatch, and a missing
mandatory tier cannot aggregate to approval. The proposed deletion was not
executed and no plausible approval path was demonstrated.
