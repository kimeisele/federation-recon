## 1. Does it ask the questions that found today's defects?

Partially. Questions 1–5 are honest distillations of real moves:

But three moves that produced today's most expensive findings are **absent**:

**(a) Open the data. Verify the change's factual premises against reality.** The single most damning finding of the day — the unsigned, unknown-source, wildcard-target message sitting live in the Nadi hub — did not come from red-teaming a mechanism. It came from refusing to accept the spec's premise ("`correlation_id` empty in all 9,874 messages"), counting for myself, getting 9,873, and **reading the one outlier**. The Nadi review opened with a line-by-line table checking every claimed premise against the code and found one false and one dangerously understated (the `clear_outbox` data-loss bug). Similarly, PR #46's review asked "is the committed zero honest anyway?" and answered it with an independent `gh api` search — distinguishing *right value* from *working instrument*. The template never asks: are the factual claims in the PR description, commit messages, and committed artifacts true? Does the committed data say what the author says it says? Read the outliers. This is `operator-lessons.md`'s own most expensive lesson ("Do not verify a property by proxy... open the data — especially the outliers") — merged this morning, absent from the template this evening. The template tells the reviewer to *read* operator-lessons.md, but its questions do not *encode* the lesson, and today proved reading does not transfer ("says 'do not verify by proxy', and I violated it hours later").

**(b) Review the substrate, not just the diff.** "The change under review is the raw diff appended below, in full" scopes the review to the diff. A diff-scoped reviewer answers "how do you defeat this?" about the new code and never learns the new code stands on sand. Under this template's own REJECT-with-conditions flow, verifying the conditions were genuinely met is the second half of the mechanism, and nothing asks for it.

## 2. The blind spot

Named concretely: **the template only catches defects where a mechanism returns the wrong answer. It cannot catch a change that is flawlessly implemented and is the wrong thing.**

The preamble even confesses this by celebration: "None was an architectural misjudgement." All seven corpses are verification-shaped, so all seven questions are verification-shaped. A PR that is well-tested, fires in CI, mutation-hardened, honestly documented — and that quietly ratchets operator authority, entrenches a bad interface, solves a problem nobody has (9,874 messages, zero work — the Nadi §6 critique), or adds a dependency the federation cannot sustain — passes Q1–Q6 clean and lands in Q7's "anything else," which is where checklist attention goes to die. Relatedly: a diff review is structurally blind to **omissions** — the missing scheduled job, the missing positive control, the missing question in a review template. Today's findings included both kinds and the template systematizes only one.

Second, sharper blind spot, which overlaps with question 5 below: every question treats the reviewed mechanism as the *defense* and a hypothetical "motivated party" as the attacker. There is no question for the case where **the diff itself is the attack** — a change that weakens, bypasses, or narrows an existing gate, test, or constraint. Q1's framing ("assume a motivated party who wants the outcome the mechanism forbids") points the gun the wrong way for that case.

## 3. The no-conditional-approval rule

Right in principle, incomplete in mechanics, and it has a perverse interaction the author did not flag.

Right: the verdict line is the only machine-parsed and (empirically, per #55) the only human-parsed bit of the report. A transport that loses everything below the verdict line must carry the blocking bit *in* the verdict. "APPROVE with unmet blocking conditions" was demonstrated today to equal "APPROVE." Collapsing it to REJECT is correct given that transport.

Incomplete: the template never says what to do with genuinely minor findings. Read literally, "approve **with conditions** → REJECT" only forces REJECT when findings are *blocking*; nits can accompany an APPROVE. But it never says so, never defines the blocking/non-blocking line, and never requires the operator to respond to non-blocking findings. So minor findings under this rule either (i) get silently dropped by reviewers who don't want to trigger the REJECT ceremony, or (ii) get inflated into REJECTs, adding noise. Fix is one paragraph: "Non-blocking findings may accompany APPROVE; the operator must respond to each in writing before merge; anything you would want verified before merge is blocking, and forces REJECT."

The perverse interaction: in this repository REJECT is *expensive* — the consultation gate requires a REJECT to be overridden by a second artifact from a third provider. Forbidding conditional approval while making rejection costly creates pressure on a reviewer to **downgrade blockers to nits** to spare everyone the process. The template should name that pressure, because a template that creates an incentive and doesn't name it will be gamed by its own users in good faith.

## 4. The seven-corpse preamble

For: concrete beats abstract, especially for a model reviewer with no memory of today. The corpses are the argument; "right-looking answer for the wrong reason" is a genuine defect *class* and seven instances of one class teach the class, not a lookup table. A future reviewer who pattern-matches to "does this pass for the wrong reason?" is anchored *usefully*. The PR body's claim ("shows the corpses rather than asserting the principle") is fair.

Against: the anchoring is real and it compounds the §2 blind spot. All seven corpses are mechanism/verification defects, so the preamble tells the reviewer, at priming strength, that this is what defects look like here. Design defects, data defects, false premises, and self-serving diffs are not in the morgue, so attention is actively steered away from them. And the preamble is frozen: dated 2026-07-25, it will age into history, and a checklist whose examples stop matching the live defect distribution decays into ritual while still feeling rigorous — the exact failure mode the PR body warns about.

Decision: keep it, with two amendments. (1) Make it an explicitly **append-only ledger** ("when a defect defeats this template, add its corpse here") so it tracks the live distribution instead of memorializing one day. (2) Add one line stating what the list does NOT contain — no architectural, data-honesty, or self-dealing corpses yet — so the anchor carries its own counterweight.

## 5. Where it goes easy on the operator

This is the template's real weakness, and it is a weakness of *absence*, which is the hardest kind to see — which is presumably why it survived.

1. **No self-serving question.** The constitutional sibling asks whether a change serves its author; this one does not, despite covering the artifacts where the operator has the most day-to-day room to move (code, gates, CI). The most probable self-interested operator change is not a bad new mechanism — it is a diff that loosens an *existing* one: an added `|| true`, a narrowed trigger path, a test deleted as "flaky", a token scope widened, a gate's file list missing one new constitutional file. No question asks "does this diff weaken, bypass, or narrow any existing check, and does the author benefit?" Q1's attacker framing points outward, never at the author.

2. **No question about the honesty of the operator's own claims.** Q4 asks what *the mechanism* claims versus proves. Nothing asks what *the author* claims versus did. Today's record includes an operator claiming "re-run live" when the timestamp proved otherwise, and a PR (#53) whose description's central claim ("CI rejects any PR...") was false in CI. "Check every factual claim in the PR description against the repo, the data, and the CI logs" is the question a hostile reviewer of this operator would put first. Its absence is the single most convenient omission for the party that wrote the template.

3. **The operator-facing section is prose, from the author of "prose did not slow the failure down."** The fix for the #55 verdict-line failure is an exhortation: "Read the whole document, not the verdict line." The PR body's own thesis is that this exact move does not work — `operator-lessons.md` said "do not verify by proxy" and was violated hours later by its author. The mechanical fixes are obvious and absent: require the operator to commit a point-by-point written response to every finding before merge, or make the no-conditional-approval rule's other half enforceable (a REJECT lists numbered conditions, the follow-up must quote and address each number). The template holds every reviewed mechanism to "method, not prose" and holds the operator's own obligation to prose.

4. **No enforcement wiring, and by its own Q2 it is therefore a prop.** Nothing triggers this template. No workflow, no gate, no required artifact path for code red-team reports (the consultation gate covers constitutional files only). "Does it fire in the environment it was built for? A gate untested under real runner conditions is a prop" — applied to itself: a review prompt that no process invokes fires exactly as often as someone remembers, which is the pre-template status quo. The PR body says "documentation only" as if that were a scope virtue; for a document whose stated purpose is to be *the standing* red-team prompt, unwired is unfinished. At minimum the template should define where its reports get committed, so their absence is greppable.

5. **A structural contradiction that flatters the cheap path.** "Send this verbatim, plus the complete raw diff" describes a diff-only consultation. But Q1 demands *executed* evasions and Q3 demands *run* mutations — impossible for a reviewer holding only a diff. A diff-only reviewer will answer Q1 and Q3 with imagined evasions and imagined mutations, exactly the currency Q1 says is worth five times less, while the report format makes imagined and executed answers look alike unless the reviewer volunteers the difference. The template must say which mode it is: if the reviewer lacks an executable checkout, Q1/Q3 answers must be labeled "not executed," or the review must be run by an agent in a checkout. Today's reviews were all checkout-mode; the template's delivery instruction describes consultation-mode. That gap will be filled by whichever is cheaper, and the cheaper one is the weaker one — an operator-favoring default.

## 6. Anything else

- **Report destination and provenance are unspecified.** Reviewer name, provider, date — the consultation artifact requires them, this template doesn't. A red-team report with no named provider is unfalsifiable as an independence claim.
- The instruction "Read CLAUDE.md, docs/operator-lessons.md, and the relevant procedure docs" front-loads context. Fine, but note the tension: the reviewer is being handed the operator's framing documents before the diff. For the constitutional sibling that is the point; for adversarial code review, consider instructing the reviewer to form the attack list *before* reading the author's rationale, then reconcile. Today's Nadi review did premise-checking precisely because it distrusted the framing.
- Small good things worth saying: the executed-vs-imagined distinction in Q1 is the best line in the file and is genuinely what separated today's reviews from theater. Q3's mutation language ("any check whose removal leaves tests green is not tested, whatever the coverage says") is exactly right. The self-aware line "a rubber-stamp review is worse than no review" is correct and the document mostly earns it.

## Verdict reasoning

The template is a faithful record of about 70% of what worked today, and the 70% it captures, it captures well — Q1's executed-evasion standard and Q3's mutation standard alone would make future reviews better. But it will shape every future review, so its omissions become universal omissions, and the omissions are not random: the missing questions (verify premises, open the data, author-as-adversary, honesty of the author's claims, self-application, substrate beyond the diff) are precisely the ones that bear on the operator that wrote it. Under the template's own rule — blocking items mean REJECT, not APPROVE-with-conditions — these are blocking, because merging the template as-is standardizes reviews that would have missed the unsigned mailbox message, the false Nadi premise, and the loosened-gate class of self-dealing diff entirely.

Blocking conditions:

1. Add a question requiring verification of the change's factual premises against reality: check the PR description's and commit messages' claims, open the committed and referenced data, and read the outliers. This is operator-lessons' costliest lesson and its absence from the template that cites the lesson is disqualifying.
2. Add a question directed at the author as adversary: does this diff weaken, bypass, narrow, or delete any existing gate, test, or constraint, and does the author benefit? Include self-application: run any new check against the PR that introduces it.
3. Widen scope beyond the diff: the reviewer must read what the diff calls, what is supposed to call the diff, and the data it runs on.
4. Resolve the diff-only vs checkout contradiction: either require an executable checkout, or require unexecuted Q1/Q3 answers to be labeled as such.
5. Define handling of non-blocking findings (may accompany APPROVE; operator must respond in writing to each) and require REJECT conditions to be numbered with the follow-up quoting and addressing each number — method, not the "read the whole document" exhortation.

Non-blocking, do when convenient: make the corpse list append-only with a stated coverage gap; name the reviewer/provider/date header requirement; name the downgrade-pressure created by costly REJECTs; specify where reports are committed.

verdict: REJECT
