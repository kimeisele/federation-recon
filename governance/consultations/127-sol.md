## 1. How do you defeat this?

Enumerated from cheapest to most expensive. Marked **[EXECUTED]** where I demonstrated the evasion.

### Evasion 1: approved_by is not checked for builder identities **[EXECUTED]**

The validator checks `acceptance_bundle.author` against `BUILDER_NAMES = ('jcode', 'deepseek', 'builder', 'worker')` via case-insensitive substring match. It does **not** apply the same check to `acceptance_bundle.approved_by`. An order where `author` is a human and `approved_by` is `"jcode"` passes exit 0, silent stderr.

```python
order = {
    ...
    "acceptance_bundle": {
        "author": "kimeisele",
        "approved_by": "jcode",  # builder name — unchecked
        ...
    }
}
# → exit 0, silent
```

Time to execute: ~1 minute. ADR §10 requires the bundle be "never produced or altered by the builder under test." A builder approving the bundle is altering it in a substantive sense: the approval is part of the run record and directly controls whether the order proceeds.

### Evasion 2: self-approval **[EXECUTED]**

`author == approved_by == "kimeisele"` passes. The validator imposes no separation between the person who wrote the acceptance criteria and the person who approved them. This is the `wo-98-3` class (issue #103) encoded as a single order: the graded party grades themselves.

Time to execute: ~1 minute.

### Evasion 3: the validator has no caller

No code in this repository invokes `core.orders.validate`. Not `core/launcher.py`, not `operator/heartbeat.sh`, not any workflow file, not `scripts/gate.sh` (which runs the *tests* but not the validator itself). The validator is a library without a consumer. An order reaches the execution path without passing through this gate because the gate is not on the path. **[EXECUTED — confirmed by grep of the entire codebase for `core.orders.validate` and `import.*validate`: zero production callers.]**

### Evasion 4: bundle digest and location are format-checked, not verified

The validator checks that `digest` matches `sha256:[0-9a-f]{64}` and that `location` starts with the required prefix. It does not verify the digest matches the bytes at that location, nor that the location exists. Any syntactically valid digest passes.

### Evasion 5: bundle created_at is format-checked, not compared

The validator checks `created_at` matches `YYYY-MM-DDTHH:MM:SSZ`. It does not compare this timestamp against the build run's start time. A bundle "created" after the build run passes.

### Evasion 6: approved_by can be empty aside from control characters

The validator checks 1–64 chars, no control characters. An approved_by of `"."` (one period) passes. The field has no semantic validation beyond length and character class.

**Evasion 1 is the most damaging and simplest. It requires zero knowledge of internals — just put a builder name in the wrong field. Evasion 3 is structural: it does not matter how correct the validator is if nothing runs it.**

## 2. Does it fire in the environment it was built for?

**No.** The validator has no production caller. `core/orders/validate.py` is never imported or invoked by any script, launcher, workflow, or scheduled job in this repository. It fires only inside its own test suite (`order-validator.bats`, `order-vectors.bats`).

The test suite exercises the validator, and the test suite runs inside `gate.sh` (step 3/4), so a passing gate implies the validator passes its tests. But the validator itself — the mechanism that decides whether an order may execute — is never consulted before execution. The gate tests the validator; nothing uses the validator.

Under a detached HEAD or shallow clone: the validator uses `__file__`-relative path resolution, not git, so it would function if called. But nothing calls it.

## 4. What does it prove, versus what does it claim?

**What it proves:** that the order document is structurally well-formed JSON matching the fixed schema, that required capabilities are named in the policy, that limit reductions are non-negative, and that the bundle's `author` field and `location` field have acceptable shapes.

**What it claims (per CONTRACT.md §1):** the order is "admissible" — the supervisor can proceed.

**The gap:** admissibility here means "no structural defect detected," not "the order is safe to execute." CONTRACT.md §5 acknowledges this honestly: *"A green validator establishes that the order claims a well-formed provenance — per ADR §3.3, a claim, not a finding."* The validator cannot and does not claim to verify:
- That the bundle digest matches actual bytes (S3 concern)
- That the bundle was created before the build run (S3 concern)
- That the approval is genuine and from an independent party (S3 concern)
- That the issue exists or the base_sha is reachable (out of scope)

This is not overclaiming. The documentation is honest. The validator is correctly scoped as S2: structural validation, not semantic verification.

## 4b. Do the change's factual premises hold?

**Premise 1: "The schema makes a looser limit structurally impossible via non-negative reductions."** HOLDS. I attempted to construct an order with a wider effective limit than policy allows:
- Negative reduction → `E_SCHEMA` (integer minimum: 0, enforced)
- Key not in policy limits → `E_SCHEMA` (unknown key rejection)
- Float reduction → `E_SCHEMA` (isinstance + bool guard)
- Zero reduction → accepted (neutral, not wider)
- Omitted limit_reductions → policy limits apply (not wider)
- Bool reduction → `E_SCHEMA` (`isinstance(val, bool)` guard)

No order document can express a wider limit than the policy. The impossibility is in the type system, not a comparison.

**Premise 2: "The capability enum is derived from the policy at runtime."** HOLDS. Verified by reading `policy.json` and tracing the code: capabilities are loaded from `claimed_capabilities ∪ unclaimable_capabilities.keys()` at validation time, not hardcoded. Adding a capability to the policy and passing its canary makes it available without code changes.

**Premise 3: "Earlier row wins per CONTRACT.md §2."** HOLDS. Verified by mutation 1: removing the size check caused the oversize vector to report E_SCHEMA (it fell through to schema validation), confirming the ordering matters and size fires first.

## 5. Which failure mode looks like success?

1. **approved_by is a builder name → exit 0, silent.** The validator checks `author` but not `approved_by`. An order approved by the builder looks identical to a properly approved one.

2. **Self-approval → exit 0, silent.** `author == approved_by == same person` passes all checks.

3. **FileNotFoundError → E_SIZE, exit 1.** A nonexistent file or a directory path reports E_SIZE, not a dedicated "file not found" code. The refusal is correct (fail-closed), and the human explanation names the problem, but a caller reading only the code gets the wrong category. This is acknowledged as issue #126.

4. **Missing policy.json → uncaught FileNotFoundError.** If `core/policy.json` is absent, `_load_policy()` raises an uncaught exception with a Python traceback as the first stderr line — the same class of defect that vector 34 was added to prevent. The traceback is still exit 1 (fail-closed), but a caller parsing the first line gets a stack frame instead of a reason code.

## 6. What would nobody notice during a long unattended session?

Nothing. The validator is a pure function with no accumulated state, no caches, no counters, no drifting thresholds. It reads two files and exits. There is nothing to degrade over time.

If it were wired into production, a changing `policy.json` would silently change which orders are accepted — but that is by design (the policy is the authority). The only silent drift would be a deletion of `policy.json` causing traceback-on-first-line (finding #5.4 above).

---

## 7. Is this the right thing, not merely a correct thing?

Yes. Structural validation before execution is the correct architecture. The validator occupies the right position in the execution core: between order receipt and any workspace creation, backend call, or model invocation. It is pure, deterministic, and small enough to audit by reading (~490 lines). The decision to derive capabilities from the policy at runtime rather than hardcoding them is correct. The reduction encoding for limits is elegant and genuinely prevents the looser-limit problem structurally.

The approach is well-tested, honestly documented, and correctly scoped to S2 (structural validation, leaving semantic verification to S3). The missing wiring (finding #1.3) is a deployment gap, not a design flaw.

## 8. What is missing?

1. **A caller.** No production code invokes the validator. Without one, the entire mechanism is inert. The minimum viable caller would be a function in `core/launcher.py` that runs the validator before `check_capabilities` and refuses the order on non-zero exit.

2. **approved_by provenance check.** The validator should check `approved_by` against `BUILDER_NAMES` with the same case-insensitive substring match applied to `author`. Without it, Evasion 1 is available.

3. **A test vector for builder-approved bundle.** A vector where `approved_by` is `"jcode"` (or any builder name) and `author` is not, expecting `E_BUNDLE_PROVENANCE`. This would make the gap testable.

4. **Policy-file error handling.** `_load_policy()` should catch `FileNotFoundError` and `OSError` and call `_refuse` with a proper reason code rather than letting the exception propagate. The current behavior is fail-closed but violates the "bare reason code on first stderr line" contract.

5. **A dedicated refusal code for unreadable input.** As acknowledged in issue #126, `FileNotFoundError` and directory paths report `E_SIZE`. A distinct code (e.g., `E_ACCESS`) would make the failure unambiguous to a caller that only reads the code.

6. **A scheduled or triggered invocation.** Per the review template preamble: *"Nothing triggers this template."* Nothing triggers the validator either. The consultation gate for constitutional files exists; no equivalent gate exists for code changes to the execution core. A CI workflow that runs the validator against a sample order on every PR would establish that the mechanism fires in its intended environment.

## 11. Anything else materially wrong or dangerous

### 11.1 The depth pre-scan accepts unbalanced input

`_check_depth` returns `True` for `{{{}` (more opens than closes) and `{}}` (more closes than opens). This is benign because the JSON parser will reject unbalanced input later, and the scan is only a resource limit check. Not dangerous.

### 11.2 The substring match in author check is broad

`BUILDER_NAMES = ('jcode', 'deepseek', 'builder', 'worker')` with substring matching catches false positives like "Shipbuilder Industries" (contains "builder") and "Deepseeker" (contains "deepseek"). This is documented in vector 31 as deliberate: *"A provenance rule that a rename defeats is not a rule, and a wrongly-refused order costs one edit while a wrongly-accepted one costs the oracle."* The tradeoff is reasonable.

### 11.3 Vectors 34 and 35 — oracle compromise assessment

The review commit (57057ed) discloses plainly: *"these two vectors were written after seeing the implementation, unlike the other 33."* The disclosure is adequate. The vectors test a rule already stated in CONTRACT.md §3 (capability names are strings from an enum), not a new rule. The contract did not move; only its coverage improved. The disclosure is more honest than pretending otherwise would be. The oracle is not compromised.

### 11.4 Issue #126 — deferral assessment

The review commit acknowledges: *"a missing, unreadable, or directory path reports E_SIZE. The refusal is correct and fail-closed; the code is not, and the contract never said what it should be."* Deferring this is right. The behavior is fail-closed (exit 1), the human-readable explanation names the actual problem, and introducing a new reason code changes the contract. The issue (#126) states the problem honestly: the wrong code is reported, the refusal is correct, and a decision is needed on what code to use.

### 11.5 The gate passes but does not establish what it cannot

`scripts/gate.sh` exits 0. Its own output correctly notes: *"Not established by this gate: that a test fails when the thing it guards breaks... that the change is the right thing rather than a correct thing... that an independent reviewer of a different provider has seen it."* This honesty is the correct posture.

## Verdict

The validator is well-designed, well-tested, pure, and honest about its scope. The two structural gaps — `approved_by` unchecked for builder identities, and the validator having no production caller — are individually rejectable. The first is a one-line fix plus a test vector. The second is a deployment gap: a correct mechanism that nothing invokes is a prop, and the review template's preamble on props applies with equal force here.

**Conditions for approval:**

1. Add `approved_by` to the builder-identity check (same case-insensitive substring match against `BUILDER_NAMES` applied to `author`).
2. Add a reject vector where `approved_by` is a builder name and `author` is not, expecting `E_BUNDLE_PROVENANCE`.
3. Wire the validator into the execution path: `core/launcher.py` (or its successor) must call `core.orders.validate` before any workspace creation or backend call, and refuse the order on non-zero exit.
4. Add error handling in `_load_policy()` so a missing or unreadable `policy.json` produces a proper reason code on stderr line one, not a Python traceback.

verdict: REJECT
