## Raw review

## Third Review: per-run uid pool architecture

### What is sound

The core primitives are well-chosen. `os.mkdir` as mutual exclusion for slot claims is atomic and correct. The double-observation pgrep pattern in `_release_slot` (observe zero, wait, confirm still zero) is a genuine improvement over single-sample. The claim-time pgrep+kill+dirty-slot cleaning closes the ABA problem properly — a newly claimed slot that has survivor processes gets them killed before the run starts. `env -i` isolation, `O_NOFOLLOW` + `S_ISREG` file discipline, and the `_EGRESS_ALLOWLIST` filter are all solid. The stop loop in `worker_kill_self.sh` converges correctly: each iteration STOPS newly-appeared processes, the per-uid `RLIMIT_NPROC` caps the population at 64, and `KILL -9` runs regardless of whether the loop converged.

---

### Findings

**F1 [HIGH]. `inside_test.txt` is not in the egress allowlist — write_inside content verification is dead code.**

`_EGRESS_ALLOWLIST = {"result.json", "escapee.pid"}`. The inner-workspace file `inside_test.txt` is never copied to the host workspace. Both `fs_confinement` and `no_network` canaries have blocks (fs_confinement lines 1264–1281, no_network lines 2086–2099) that read `tmp/inside_test.txt` and compare checksums — but `os.path.exists(inside_path)` is always `False`. The verification is silently skipped. The only check that executes is the payload's self-reported `outcome` field: a corrupted payload that claims `"allowed"` while writing garbage passes.

Additionally, the payload writes `"should-succeed"` (line 3249) while the dead verification code expects `"canary-write-test"` (line 1271) — the mismatch is masked by the egress filter. If the file were ever added to the allowlist, the canary would break.

**Specific consequence**: A compromised or buggy payload can report `"allowed"` for `write_inside` while writing nothing, or writing to a different path. The canary cannot detect this. This is the preservation half of two capabilities; a corpse (dead filesystem) is detected by `outcome == "blocked"`, but a liar is not.

**Fix**: Add `"inside_test.txt"` to `_EGRESS_ALLOWLIST` and align the expected content between payload and canary.

---

**F2 [HIGH]. Reconcile deletes just-created run directories and claim directories under concurrency.**

In `run()`, the sequence is:
```
os.mkdir(inner_ws)                          # line 832 — run dir created
_claim_set_run_id(slot_name, run_id)         # line 841 — mapping written
```

Between these two lines, `reconcile()` (called at launcher startup and after the suite) can:
1. List `_SLOTS_DIR`, find the claim directory, call `_claim_get_run_id()` → `None` (not written yet)
2. List `_RUNS_DIR`, find `inner_ws`, its `run_id` not in `claimed_run_ids` → `shutil.rmtree(path)` — **deletes the inner workspace**
3. Check the slot's pgrep → rc=1 (no worker process started yet) → `shutil.rmtree(claim_dir)` — **deletes the claim directory**

Then `_claim_set_run_id()` runs but the claim directory is gone (silent return). `os.listdir(workspace)` succeeds, but `_copy_ingress` fails because `inner_ws` was deleted. `os.chmod(inner_ws, 0o777)` raises `FileNotFoundError`. The run fails. The finally block tries `shutil.rmtree(inner_ws)` (already gone), then `_release_slot` → kill_slot finds nothing, pgrep empty → release (already gone).

**Specific consequence**: Spurious run failures when `reconcile()` and `run()` execute concurrently. The design explicitly permits concurrency up to pool size, so two launcher instances (or launcher + manual reconcile) trigger this. Not a security leak (slot is released, no orphaned processes) but a reliability failure.

**Fix**: Call `_claim_set_run_id()` before `os.mkdir(inner_ws)`, or have reconcile use the claim directory's bare existence (not the run_id file) as proof a run directory is legitimate.

---

**F3 [MEDIUM]. `_SLOTS_DIR` is not runtime-verified for write permissions.**

`_verify_runs_dir_secure()` checks `_RUNS_DIR` for group/world writability but does not check `_SLOTS_DIR`. If `_SLOTS_DIR` is world-writable — due to misconfiguration or drift — any unprivileged user can:
- `mkdir /usr/local/var/jcode-runs/slots/_jcode_w01` → slot appears "claimed," blocking allocation
- `touch /usr/local/var/jcode-runs/slots/_jcode_w01.quarantined.0` → slot appears "quarantined"
- Exhaust all 8 slots, denying service to legitimate runs

**Specific consequence**: Pool-exhaustion DoS without root. Only `_RUNS_DIR` is checked; `_SLOTS_DIR` is assumed correct from setup time.

**Fix**: Extend `_verify_runs_dir_secure()` to also check `_SLOTS_DIR`, or add a `_verify_slots_dir_secure()` call.

---

**F4 [MEDIUM]. `_quarantine()` rename failure silently leaks the claim directory.**

```python
def _quarantine(slot_name, reason):
    claim_dir = os.path.join(_SLOTS_DIR, slot_name)
    q_dir = os.path.join(_SLOTS_DIR, f"{slot_name}.quarantined.{ts}")
    try:
        os.rename(claim_dir, q_dir)
    except OSError:
        pass  # ← claim_dir persists, slot stays "claimed"
```

If `os.rename()` raises (e.g., `ENOSPC`, `EROFS`, `EIO`), the claim directory is not moved. `_quarantine()` returns silently. `pool_status()` sees the slot as "claimed." No run owns it. It never auto-clears (quarantine has no auto-clear; reconcile only releases empty slots). The slot is **permanently leaked**.

**Specific consequence**: Each rename failure permanently removes one slot from the 8-slot pool. After enough failures, `NoSlotAvailable` on every request. The error is not logged — the `OSError` is caught with `pass`.

**Fix**: Log the rename failure, and attempt `shutil.rmtree(claim_dir)` as a fallback before giving up.

---

**F5 [MEDIUM]. `_release_slot()` ignores `kill_slot()`'s return value — kill failure is silent.**

Line 509: `kill_slot(slot_name, slot_uid)` — the returned `{"ok": ..., "returncode": ..., "stderr": ...}` dict is not assigned or checked. The pgrep polling loop runs regardless. If `kill_slot()` fails because `sudo` is missing, the kill-self helper is not found, or the invocation times out after 15s, the release loop still polls pgrep and may release the slot if processes happened to exit on their own.

**Specific consequence**: If kill_slot fails but no processes remain (worker exited cleanly), the slot is released normally — acceptable. If kill_slot fails AND processes are still running, the pgrep loop polls for 10s, then quarantines — also acceptable, but the quarantine reason doesn't mention that kill_slot failed. The failure mode is silent. An operator diagnosing "processes still present after 10s deadline" needs to independently discover that the kill never ran.

**Fix**: Check `kill_result["ok"]` and include the stderr in quarantine/log messages if the kill failed.

---

**F6 [LOW]. `_marker_in_workspace()` in `symlink_egress.py` uses `os.path.isfile()` — follows symlinks.**

```python
def _marker_in_workspace(workspace, marker):
    for fn in os.listdir(workspace):
        path = os.path.join(workspace, fn)
        if not os.path.isfile(path):   # ← follows symlinks
            continue
```

This violates the codebase's own "never `os.path.isfile()` on an untrusted path" discipline. While the host workspace is trusted (created by the canary orchestrator), the inconsistency is dangerous: if a previous canary's cleanup fails and leaves a symlink behind, this function follows it. Not exploitable today but the discipline exists for a reason.

**Fix**: Use `os.lstat(path)` + `stat.S_ISREG(st.st_mode)` or the existing `_secure_open_read()`.

---

**F7 [LOW]. `worker_kill.sh` is dead code — targets obsolete shared uid `_jcode_worker`.**

The file at `core/worker_kill.sh` runs `pkill -9 -u _jcode_worker`. In the per-run uid pool architecture, no such user exists. The active kill path uses `worker_kill_self.sh` with per-slot uid derivation via `id -u`. No code references `worker_kill.sh`. Its presence in the `/core/` trust boundary is confusing: a future maintainer might wire it up, or an attacker examining the boundary might exploit the confusion.

**Fix**: Delete `worker_kill.sh` or replace it with a stub that exits 1 with a clear message.

---

### Verdict

**REQUEST CHANGES** — F1 and F2 are blocking.

F1 means the preservation halves of `fs_confinement` and `no_network` canaries cannot verify write content. A payload that lies about `write_inside` passes undetected. This weakens the pair architecture for two capabilities.

F2 means the reconcile function, which is the replacement for `finally`-path cleanup, can destroy active runs under the concurrency the design explicitly permits.

F3–F7 are non-blocking but F4 (silent permanent slot leak) should be addressed before production use of the pool.
